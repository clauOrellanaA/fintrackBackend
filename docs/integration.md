# Integracion prevista

## Estado de arranque local

Las aplicaciones tienen scripts y dependencias. Consultar el [README](../README.md) para `npm ci`, `npm run setup`, migraciones, seed y comandos de inicio. El frontend comprueba `/api/v1/health`; `/api/v1/health/ready` verifica PostgreSQL mediante `pg`. Estas rutas no sustituyen autenticacion ni persistencia TypeORM, implementadas en BE-01.

Navegador React (localhost:5173) -> HTTP/JSON -> API NestJS (localhost:3000/api/v1) -> PostgreSQL (localhost:5432).

El frontend nunca se conecta directamente a PostgreSQL y no recibe credenciales de base de datos ni secretos JWT. Las variables VITE_* son publicas.

Copiar .env.example a .env en cada repositorio y sustituir los valores de ejemplo. No subir .env a Git. CORS_ORIGIN del backend debe coincidir con el origen del frontend. DATABASE_URL debe coincidir con las credenciales POSTGRES_*; si la contrasena tiene caracteres especiales, codificarla para una URL.

La composicion Docker reside en fintrackBackend/compose.yaml. Incluye solo PostgreSQL en esta etapa: ejecutar docker compose --env-file .env config para validar y docker compose up -d database para iniciar. Requiere Docker Compose instalado. El volumen conserva datos entre reinicios.

Las aplicaciones se ejecutan localmente con npm. Para contenerizarlas en una etapa posterior, agregar Dockerfiles y servicios frontend/backend al mismo Compose. Dentro de Docker, el backend usara database:5432; el navegador seguira usando una URL accesible desde el host para la API.

Contrato aprobado en [dashboard-contract](dashboard-contract.md) y [OpenAPI v1](openapi/dashboard.v1.json). BE-01 incluye login/logout, sesiones bearer opacas sin cookies, guard, esquema/migracion y seed. Dashboard valida mes en America/La_Paz; BE-02 devuelve balance ready con amount cadena decimal y cutoff igual a asOf, independiente del mes seleccionado. BE-03 devuelve monthlySummary ready con data.income/data.expense cadenas exactas de dos decimales. BE-04 devuelve expenseDistribution ready con data como lista de categoryId/categoryName/amount/percentage. BE-05 devuelve budgets ready como lista de id/categoryId/categoryName/limit/spent/remaining/progress/state; BE-06 devuelve savingsGoals ready con objetivo, acumulado, restante, progreso, estado y fecha opcional. Las cinco secciones estan disponibles. Seed octubre2026 conserva alice income0.00/expense500.05 en Alimentacion100.00%, bob income0.00/expense40.50 en Transporte100.00%, saldos anteriores a reservas2500.05/859.50 y budgets[]. Con reservas reales BE-06 de300.00/600.00, el disponible al2026-10-19 es2200.05/259.50, sin alterar ingresos/gastos. Seed febrero2026 agrega tres presupuestos por usuario y movimientos compensados neto0. Errores usan envelope error.code/message sin SQL ni secretos; respuestas privadas no-store. Hay pruebas HTTP/PostgreSQL reales de acceso e indicadores implementados. BE-07 verifica el contrato completo mediante JSON Schema y HTTP/PostgreSQL. La integracion con frontend, CRUD completos y paginacion de futuras listas publicas siguen fuera de este cierre backend.

Overflow de saldo devuelve 422 DATA_OUT_OF_RANGE; apertura aun no efectiva o datos monetarios invalidos devuelven 500 DATA_INTEGRITY_ERROR. Usuario inexistente no obtiene apertura cero. Fallos abortan toda respuesta y nunca se convierten en saldo cero. BE-06 conecta SavingsReservationReader a las reservas persistidas, incluidas las metas archivadas, dentro del snapshot del saldo. Aportes reservan y retiros liberan, sin modificar ingresos/gastos.

Resumen mensual usa inicio inclusivo y fin exclusivo del mes elegido, tambien si es futuro; un posted posterior a asOf puede aparecer en el resumen sin afectar todavia al saldo. No se suman monedas distintas, no se incluyen anulados y no se compensan devoluciones contra gastos: son ingresos brutos. Mes vacio devuelve income0.00/expense0.00 solo tras consulta exitosa. Overflow de cualquiera de los totales devuelve422 DATA_OUT_OF_RANGE aunque el neto se compense. Fallos de resumen abortan la respuesta completa sin conservar un balance parcial. Saldo y resumen comparten snapshot REPEATABLE READ y un unico asOf en dashboard.

Distribucion usa exactamente esos filtros mensuales y el mismo snapshot, incluidos posted futuros del mes. Sin categoria: categoryId null y categoryName Sin categoria. Sin gastos: lista vacia, nunca un segmento inventado. Importe y porcentaje son cadenas de dos decimales; orden importe descendente, luego categoryId ascendente con null ultimo en empate. HALF_UP independiente admite desviacion respecto100 de hasta0.005 puntos porcentuales por categoria: tres tercios33.33 suman99.99; importes1/31 sobre32 producen3.13/96.88 y suman100.01. No corregir importes ni porcentajes para forzar100. Fallo de distribucion aborta todas las secciones y no devuelve[] artificial; overflow del total conserva422 DATA_OUT_OF_RANGE.

Presupuesto exige categoria existente del mismo usuario (UUID no nulo) y limite positivo. Consumo mensual bruto usa API publica de gastos bajo el mismo snapshot; restante=limite-consumo puede negativo, progreso exacto redondeado HALF_UP puede superar100. Estado se decide antes del redondeo:79.999% es normal aunque se muestre80.00;100.001% es exceeded aunque se muestre100.00. Un100% exacto es warning. Orden estable categoryId ascendente y luego id. Mes sin presupuestos devuelve[], distinto de presupuesto valido sin gastos (spent0.00, progress0.00, normal). No rollover, CRUD ni notificaciones. Fallos abortan todas las secciones sin fabricar cumplimiento.

BE-06: metas visibles creadas hasta asOf y no archivadas a ese corte. Objetivo positivo; acumulado=aportes-retiros hasta asOf; restante=max(objetivo-acumulado,0); progreso HALF_UP sin limitar 100. completed precede overdue; overdue solo si targetDate es anterior al dia local America/La_Paz; hoy sigue active si incompleta. Reservas incluyen metas archivadas: ocultar no cambia fondos. Todas las consultas usan propietario, BOB y EntityManager del mismo REPEATABLE READ. Objetivos/importes invalidos se rechazan; fallos abortan toda respuesta.

Persistencia incluye FK compuesta meta/usuario, fechas posteriores a creacion/apertura, ledger de solo anexado y validacion de todos los prefijos temporales por instante. Cada entrada incrementa la version de la meta para serializar escritores y provocar 40001 ante snapshots RR obsoletos. No se promete reintento automatico ni proteccion concurrente de cambios de apertura no probados. El modulo expone CRUD controlado en [savings-goals.v1](openapi/savings-goals.v1.json): listar, crear, editar/archivar y registrar aportes o retiros. No existe DELETE destructivo: archivar oculta la meta del dashboard, pero sus reservas siguen afectando el saldo.
